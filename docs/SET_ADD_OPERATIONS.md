# Добавление подхода и восстановление после потери ответа

Gym владеет подходами и квитанциями; Core только читает обычные записи. Today,
«Все упражнения» и подробный редактор используют один механизм добавления.

Каждый новый выполненный подход получает случайный `operation_id` (128 бит).
В API это дополнительное поле JSON. Новый WebApp вызывает отдельные маршруты
`/day/{day}/exercise/{id}/set/add_once` и
`/all_exercises/exercise/{id}/set/add_once`, которые требуют ключ. На старом API
этих маршрутов нет:404 не добавляет подход, даже если backend был откачен между
проверкой версии и POST. `/whoami` объявляет `set_add_operations_version=1`; UI
проверяет поддержку, прежде чем посылать новый запрос. Старые `/set/add` сохраняются. Для запроса с ключом обязательны исходные
`reps`, `seconds`, `weight_kg`; значения по предыдущему подходу не подставляются
заново при повторе. Today также связывает `is_warmup` (по умолчанию false).
Два намеренно добавленных одинаковых подхода получают разные ключи и оба сохраняются.
Клиенты без поля остаются совместимыми и сохраняют прежний append-контракт.

`set_add_operations` записывается атомарно с `sets`, defaults и native touch в
`BEGIN IMMEDIATE`. Ключ связан с владельцем, действующим пользователем, конкретной
сессией/упражнением, поверхностью, датой и нормализованными значениями. Другой
контекст или значения с тем же ключом дают409 без нового подхода. Владелец сессии
и упражнения и актуальная trainer edit permission проверяются внутри writer при
каждом запросе, включая повтор. Receipt не предоставляет долговременный доступ.

Успешный ответ содержит `operation`: исходный `operation_id`, `set_id`,
`session_id`, `replayed` и `state` (`present`/`removed`), а также текущий список
подходов. Повтор не меняет уже отредактированный подход, не восстанавливает удалённый,
не обновляет defaults и не продлевает активность свободной тренировки. Квитанция
хранится после удаления отдельного подхода. Номер подхода может повториться после
удаления, стабильный id не переиспользуется. Квитанции сохраняются до owner wipe;
они не удаляются по короткому TTL, который позволил бы старому ключу снова создать
подход. На владельца есть индекс, wipe удаляет только его квитанции.

В WebApp неподтверждённое намерение отделено от редактируемых полей. Одновременные
активации одной кнопки объединяются, кнопка временно недоступна. Потеря ответа
не выдаётся за доказанный отказ: появляется «Проверить запись» с пояснением.
Проверка повторяет исходный ключ и значения; изменённый пользователем draft
сохраняется для следующего реального подхода. Новый ключ создаётся только после
подтверждённого результата предыдущего намерения. Поздний ответ другого аккаунта,
даты или контекста не меняет открытый экран. Нет автоматического POST retry.

Pending хранится в памяти и `sessionStorage` собственной вкладки; scope основан
на Telegram subject, подтверждённом собственным `/whoami`, а не SDK hint/guest.
Пустой `initDataUnsafe` принимающего WebApp не смешивает аккаунты. Самостоятельный
native whoami не зависит от доступности Core; несовпадение идентичности отклоняется.
Перезагрузка этой вкладки восстанавливает pending. При запрещённом storage остаётся
восстановление в памяти текущей страницы. Закрытие вкладки/очистка storage, другое
устройство и передача несохранённого draft не обещают восстановления намерения.
Дедупликация по равным весу/повторам или временному интервалу запрещена.

После объединения с owner-storage используется общий `nativeOwnerStorageScope`:
постоянный ключ отдельно различает подтверждённого viewer и acting target, систему,
дату, поверхность и упражнение. Новый proof того же владельца не теряет pending.
Для позднего ответа отдельно хранится `activeOwnerContextKey` с монотонной runtime
revision: переход A→B→A или proof→другой proof→первоначальный proof не делает старый
ответ актуальным. Runtime revision не входит в сохраняемый recovery key.
Если кнопка ждала повторной проверки `/whoami`, изменение proof, acting target,
системы, даты, поверхности или объекта упражнения отменяет исходный жест до POST.
Повторная проверка identity сохраняет общий Promise и полный предел 2500 ms
(включая JSON/body), запрос 1800 ms без автоматического GET retry; неудача оставляет
native UI доступным, но без личного cache и без неподтверждённой операции записи.

Миграция аддитивная, без новых библиотек, workers, AI или Telegram consumer. При
откате кода DB и все более поздние пользовательские записи сохраняются. Старый
клиент/код может читать обычные подходы, таблицу receipt оставляем для возврата
нового кода; новый UI не посылает добавление в старый append-only маршрут.

Проверки: `python -m unittest discover -s tests -p test_set_add_operations.py -v`
и `node --test tests/test_set_add_operations.cjs`. Python использует реальные API
writers/ASGI/SQLite на временной базе: обе поверхности, потерянный ответ/повтор,
параллельность, отдельные одинаковые подходы, context/payload/owner/actor mismatch,
trainer revoke, atomic rollback, удаление/редактирование, legacy и wipe. JS выполняет
функции из настоящего HTML и проверяет pending/double activation/reload/late result.
Отдельный локальный browser fault test использует настоящий HTML/API и вымышленные
профили, без внешней сети/провайдеров; это не physical Telegram/iPhone проверка.
